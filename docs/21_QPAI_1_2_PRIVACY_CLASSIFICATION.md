# QPAI 1.2 — Analytics Privacy and Data Classification

**Status:** Proposed control specification  
**Scope:** All Quincestone products and Statsig integrations  
**Session Replay:** Not approved; disabled by design for the initial rollout

## 1. Governing principle

Product analytics must collect the least data necessary to answer a defined product question. Statsig is a third-party processor for approved measurement data, not a Quincestone identity store, customer record system, business record system, or audit authority.

No analytics integration may weaken Supabase RLS, server authorization, human review, payment authority, or product data boundaries.

## 2. Data classes

| Class | Examples | Statsig policy |
|---|---|---|
| P0 — public product metadata | Product namespace, registered route key, feature key, schema version, environment | Allowed |
| P1 — coarse behavioral metadata | Journey stage, outcome category, item-count band, device category where approved | Allowed after event-specific approval |
| P2 — pseudonymous identifiers | HMAC-derived actor ID, HMAC-derived workspace ID, consented anonymous session ID | Conditional; purpose-limited and documented |
| P3 — personal or confidential data | Name, email, phone, raw Supabase UUID, raw workspace/customer/deal/order IDs, free text, business records | Prohibited from Statsig event payloads |
| P4 — highly sensitive/security data | Passwords, access/refresh tokens, API keys, payment credentials, authentication/recovery tokens, private documents, secrets, internal security evidence, chain-of-thought | Strictly prohibited |

Pseudonymous data can still be personal data under applicable privacy law. Pseudonymization is a safeguard, not anonymization or an exemption from consent and legal obligations.

## 3. Identity design

### Authenticated users

- Never use email, phone, username, raw Supabase Auth UUID, or a provider identity as Statsig `userID`.
- The implementation must use a stable, random-looking pseudonymous identifier generated by a trusted server-side process.
- The recommended initial mechanism is a keyed HMAC of the canonical Supabase user UUID using a dedicated high-entropy secret held only in trusted server environments. The secret must never reach the browser, source control, build logs, or Statsig.
- Use the same approved derivation across products only if cross-product identity is explicitly approved by the privacy owner. Otherwise use product-scoped pseudonyms.
- A raw workspace UUID must never be sent as a group identifier. If workspace-level analysis is approved, use a separate keyed pseudonym.
- Do not send user email, IP address, user agent, full name, or profile attributes to Statsig unless a separate documented review authorizes a specific field.

### Anonymous visitors

- Do not assume a visitor has consented to analytics because they visited a public page.
- Initialize analytics and create/persist an anonymous identifier only after the applicable consent decision.
- If consent is absent or withdrawn, do not initialize analytics collection or continue sending events.
- Do not silently merge anonymous and authenticated identities. Identity linking requires an approved consent-aware design.

### Key management

- The HMAC secret is server-only, independently generated per environment, rotatable, and accessible only to the minimum set of trusted runtimes.
- Do not use the Statsig client key as an HMAC secret.
- A client SDK may receive the resulting pseudonymous identifier, never the derivation key.
- Key rotation and identity continuity behavior must be designed and tested before production.

## 4. Collection restrictions

The adapter must reject or strip, by schema validation rather than developer convention alone:

- Names, email addresses, telephone numbers, postal addresses.
- Message bodies, notes, free-text search terms, form contents, assessment answers, support text.
- Raw user, workspace, customer, order, deal, offer, interaction, trace, review, action-execution, or provider IDs.
- Product prices, deal values, account balances, revenue, margins, payment identifiers, card/bank details, or exact commercial terms.
- Authentication data, passwords, reset links, tokens, cookies, secrets, session credentials.
- Private business documents, uploaded file names/content, policy text, workflow payloads, provider request/response bodies.
- Security findings, internal operator notes, audit evidence, model reasoning or chain-of-thought.

Where a metric needs commercial magnitude, first consider a coarse approved band. Exact value collection requires a separate business, privacy, and legal review.

## 5. URLs, forms, and browser capture

Do not enable Statsig Web Analytics auto-capture in the initial pilot.

The official Web Analytics documentation describes automatic capture of page URL and query parameters, referrer information, clicks, form submissions, copied text, JavaScript errors/stack traces, and other page context. This is broader than the approved QPAI event allowlist.

Instead:
- Use manual page-view events with registered `route_key` values.
- Never transmit raw URLs, query strings, referrer URLs, form values, selected text, or arbitrary DOM attributes.
- Never capture search text or copied text.
- Do not enable console-log capture.
- Do not install the auto-capture plugin in the initial release.

## 6. Session Replay

Session Replay is not approved for QPAI 1.2 initial rollout.

Reasons:
- Business OS includes customer and operational data.
- Deals includes confidential negotiation and commercial terms.
- Admin includes privileged internal controls and security evidence.
- Statsig's documented default replay privacy mode masks passwords only; other text and inputs may remain visible.

Any future replay proposal must include:
1. A separate privacy impact assessment and legal review.
2. Maximum baseline masking.
3. Explicit block rules for customer, workspace, deal, order, payment, assessment, review, document, and admin surfaces.
4. A documented consent/eligibility gate.
5. A low, justified sampling rate.
6. Network/body capture disabled unless specifically reviewed.
7. Retention and deletion requirements confirmed against contract and applicable law.
8. A verified test showing sensitive text, fields, and navigation data are not recorded.

## 7. Consent, notice, and user rights

Before production collection:
- Identify the Quincestone legal entity and controller/processor roles for each relevant market.
- Confirm the applicable lawful basis and consent requirements for each product and analytics purpose.
- Update the public Privacy, Cookie, and relevant product notices to identify Statsig and the actual categories of data collected.
- Provide a working consent/opt-out mechanism where required.
- Respect withdrawal and applicable access/deletion requests in the analytics workflow.
- Document cross-border processing, subprocessors, retention, and contractual safeguards.
- Do not claim compliance certification or a retention period without evidence.

No legal basis or consent state should be inferred from this specification.

## 8. Retention and deletion

Do not invent or publish a retention duration. Before production, document:
- Statsig account/project retention settings and contractual limits.
- Quincestone's source-event retention.
- How pseudonymous identities and derived events are handled for deletion requests.
- How event exports, backups, and downstream integrations are treated.
- The owner and SLA for privacy requests.

## 9. Security controls

- Client SDK keys are public identifiers and may be exposed in browser bundles.
- Server secret keys and HMAC keys remain server-only.
- No secrets in Git, browser bundles, client logs, screenshots, issue reports, or analytics.
- Apply least privilege to Statsig project access.
- Separate development, staging, and production credentials.
- Restrict access to analytics data by business need.
- Treat Statsig feature gates as product configuration, never authorization.
- Keep security/audit telemetry in the authoritative Quincestone systems.

## 10. Go-live checklist

Production collection remains blocked until every item is verified:

- [ ] Event-by-event data classification approved.
- [ ] Pseudonymous identity mechanism implemented and reviewed.
- [ ] Consent behavior tested across public and authenticated products.
- [ ] Auto-capture and Session Replay remain disabled.
- [ ] URLs, query strings, form fields, and free text excluded.
- [ ] Client/server keys separated and environment-scoped.
- [ ] Statsig project access reviewed.
- [ ] Privacy/Cookie notices updated to match deployed behavior.
- [ ] Retention, deletion, and vendor-processing details documented.
- [ ] Production payload inspection confirms only approved fields leave Quincestone.

## 11. Reference

Statsig's current Session Replay privacy documentation describes three baseline modes: Passwords (default), Inputs, and Maximum, with selector-level masking/blocking. The default is not sufficient for Quincestone's sensitive product surfaces. See https://docs.statsig.com/session-replay/privacy and https://docs.statsig.com/session-replay/configure.
