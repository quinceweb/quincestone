01 / PURPOSE

Quincestone exists to improve what happens between attention and revenue.

Most businesses have websites.

Many have forms.

Some have booking tools.

Few have a connected operational flow that moves a prospect from first interest to a qualified commercial opportunity.

Quincestone connects that journey.

VISITOR
   ↓
INTEREST
   ↓
ENQUIRY
   ↓
QUALIFICATION
   ↓
BOOKING
   ↓
FOLLOW-UP
   ↓
PIPELINE
   ↓
OPPORTUNITY

The objective is not to add more pages.

The objective is to create a clearer, faster, more measurable path from interest to action.

02 / POSITIONING

«Turn more enquiries into qualified opportunities.»

Quincestone is not positioned as a generic web-design agency.

It is not a collection of disconnected templates.

It is not a decorative marketing layer placed above weak operations.

Quincestone focuses on the operational journey between first contact and commercial action:

- how visitors understand the offer;
- how enquiries are captured;
- how prospects are qualified;
- how appointments are scheduled;
- how follow-up is triggered;
- how opportunities are tracked;
- how teams maintain visibility;
- how the complete flow is deployed and improved.

15 / DATABASE SECURITY

Every public submission table must use Row Level Security.

Expected access model:

INSERT   CONTROLLED
SELECT   DENIED
UPDATE   DENIED
DELETE   DENIED

Public users may submit valid forms.

Public users must not be able to:

- enumerate submissions;
- read customer data;
- modify submissions;
- delete submissions;
- inspect production lead records.

The browser-safe Supabase key is not a secret.

Database protection depends on:

- Row Level Security;
- narrow policies;
- database constraints;
- safe public inserts;
- no unrestricted public reads;
- no service-role credentials in frontend code.

17 / EMAIL

Email delivery should occur server-side through Resend and Supabase Edge Functions.

Expected notification types:

AUDIT CONFIRMATION
IMPLEMENTATION CONFIRMATION
CONTACT CONFIRMATION
DEMO ESTIMATE CONFIRMATION
INTERNAL SUBMISSION ALERT

A valid database insert should remain successful even when email delivery fails temporarily.

Email failures should be recorded securely without exposing infrastructure details to the user.
